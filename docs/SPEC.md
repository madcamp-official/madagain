# MINDHEXER 기술 명세서 v3
## Galaxy S24+ (카드보드 헤드셋) + Galaxy S10e (원격 컨트롤러) 구성

**변경 요약 (v2 → v3)**

1. VR 기기 구성이 Quest 기반에서 **카드보드 간이 헤드셋(S24+)** 으로 전환 → Meta XR All-in-One SDK 제외, Google Cardboard XR Plugin 도입
2. 통신 구조를 **UDP(연속 스트리밍) / WebSocket(확정 이벤트)** 로 명확히 이원화, 각각의 채택 근거 명시
3. 외부 서버·앱스토어 페이지 없이 **두 폰 간 P2P 직결** 구조로 확정
4. 인원 2명, 기간 7일, 개발 방식은 AI 보조 코딩(바이브 코딩) 활용 전제 유지

---

## 1. 전체 아키텍처

```
[Galaxy S10e : 컨트롤러 앱]  <==(로컬 Wi-Fi / 모바일 핫스팟)==>  [Galaxy S24+ : 카드보드 VR 본체]
   - 터치(스와이프) 좌표 스트리밍 (UDP)                              - UDP 수신 → 패턴 판정
   - 자이로/가속도 스트리밍 (UDP)                                    - WebSocket 서버 내장
   - 패턴 판정 결과 수신 (WebSocket)                                 - 카드보드 스테레오 렌더링
   - 페어링 요청 (WebSocket)                                        - 헤드트래킹 (S24+ 자체 자이로)
```

- 서버 없는 P2P 구조. **S24+가 WebSocket 서버 역할을 겸함** (앱 자체 내장, 별도 인프라 불필요)
- 두 기기 다 Unity Android 빌드로 통일하여 코드/패킷 구조체 공유

## 2. 통신 프로토콜 이원화 (핵심 설계 원칙)

| 데이터 | 프로토콜 | 근거 |
| --- | --- | --- |
| 터치/스와이프 좌표, 자이로 기울기·회전, 가속도 | **UDP** | 초당 수십~수백 회 갱신되는 최신 상태값. TCP 기반 WebSocket은 Head-of-Line Blocking으로 패킷 유실 시 최신 값 전달이 지연됨. UDP는 유실 패킷을 버리고 최신 값을 즉시 전달하므로 체감 지연이 낮음 |
| 패턴 인식 성공/실패, 페어링 요청/해제, 배터리 경고 등 확정 이벤트 | **WebSocket** | 반드시 도달해야 하는 저빈도 이벤트. TCP의 순서 보장·재전송이 오히려 이점으로 작용 |

### 2.1 UDP 채널 설계

- 시퀀스 번호 포함 → 헤드셋 측에서 오래된(역전된) 패킷 폐기
- 타임스탬프 포함 → 지터 계산 및 보간 기준값
- 헤드셋 측 보정 로직: 터치 좌표는 **Lerp**, 자이로 회전값은 **Slerp**로 프레임 간 보간하여 패킷 유실로 인한 끊김 완화

### 2.2 WebSocket 채널 설계

- S24+ : `WebSocketSharp` (오픈소스, 무료) — 앱 내장 서버로 포트 리스닝
- S10e : `NativeWebSocket` (오픈소스, 무료) — 클라이언트로 접속
- WebSocketSharp는 별도 스레드에서 동작하므로 Unity 메인 스레드로 콜백 전달 시 동기화 큐 필요 (자체 구현, 바이브 코딩으로 단시간 처리 가능)

### 2.3 연결 수립 순서

1. S24+ 앱 실행 시 WebSocket 서버 자동 기동 + UDP 브로드캐스트로 자신의 IP 알림
2. S10e 앱이 브로드캐스트 수신 → WebSocket 연결 시도 → 성공 시 UDP 스트리밍 시작
3. **폴백**: 브로드캐스트 실패 대비, IP 직접 입력 UI 필수 구현
4. 공유 Wi-Fi가 없는 환경 대비, **S24+ 모바일 핫스팟으로 S10e 연결**하는 방식도 코드 변경 없이 동일하게 작동 (같은 로컬망이라는 전제만 유지되면 됨)

## 3. Galaxy S24+ (카드보드 VR 본체) 측 명세

### 3.1 필요 패키지

| 패키지 | 용도 |
| --- | --- |
| **Google Cardboard XR Plugin for Unity** | 스테레오 분할 렌더링, 렌즈 왜곡 보정, 헤드트래킹(자체 자이로 기반). 공식 지원은 종료되었으나 오픈소스로 계속 동작 |
| URP | 렌더 파이프라인 |
| `WebSocketSharp` | 앱 내장 WebSocket 서버 |
| `System.Net.Sockets` (UDP) | S10e로부터 터치/자이로 패킷 수신 |
| ProBuilder | 레벨 화이트박싱 |
| DOTween | UI/이펙트 트윈 |
| Unity Behavior | 드론/터렛/CCTV AI 비헤이비어 트리 |
| VFX Graph / Shader Graph | 해킹 글리치, CCTV 적외선 연출 |

### 3.2 XRI 관련 변경사항 (중요)

카드보드 구성은 컨트롤러가 없는 **뷰어 전용 구조**이므로, XRI의 기존 역할이 축소·대체됩니다.

| XRI 기존 기능 | v3에서의 처리 방식 |
| --- | --- |
| Locomotion (컨트롤러 스틱 이동) | **대체 필요**: S10e에서 오는 스와이프/자이로 값을 자체 입력 브릿지로 받아 이동에 매핑 (예: 시선 방향 + S10e 스와이프로 전진) |
| Grab Interactor (컨트롤러로 잡기) | **대체 필요**: 컨트롤러가 없으므로 시선 기반 Gaze Interaction(응시 후 확인) 또는 S10e 터치로 대체 |
| Ray/Poke Interactor | 유지 가능하나 입력 소스를 컨트롤러가 아닌 **카드보드 자체 트리거 버튼(물리 버튼 1개)** 또는 S10e 신호로 리매핑 |
| XR Origin / Camera Rig | Cardboard Plugin의 카메라 리그로 대체, XRI의 것은 사용하지 않음 |

**결론**: XRI는 이제 "전면 골격"이 아니라 **UI 상호작용의 일부 구조(Ray Interactor 등)만 부분 차용**하는 형태로 축소됩니다. Meta XR SDK는 Quest 전용이므로 v3에서 완전히 제외합니다.

### 3.3 입력 처리 파이프라인

```
S10e UDP 패킷 수신 → 시퀀스 검증/폐기 → Lerp/Slerp 보간 → 게임 입력 이벤트로 변환
   (예: 정규화 좌표 → 3x3 해킹 그리드 좌표계 매핑)
   (예: 자이로 회전값 → 보조 연출용, 헤드트래킹은 S24+ 자체 자이로가 전담)
```

- **주의**: 헤드트래킹(시점 회전)은 S24+ 자체 센서(Cardboard Plugin)가 담당하고, S10e의 자이로는 **해킹 조작 보조용**으로만 사용해 역할 충돌을 방지

## 4. Galaxy S10e (컨트롤러) 측 명세

### 4.1 필요 패키지

| 패키지 | 용도 |
| --- | --- |
| Unity 내장 `Input System` | 멀티터치 좌표, 스와이프 궤적 캡처 |
| Unity 내장 자이로 API (`Input.gyro`) | 기울기/회전/가속도 값 획득 |
| `System.Net.Sockets` (UDP) | S24+로 좌표/센서값 스트리밍 |
| `NativeWebSocket` | S24+ 내장 서버에 이벤트 채널 접속 |

### 4.2 앱 구성

- 씬 1개, 3x3 터치 그리드 오버레이 + 연결 상태 UI만 존재 (그래픽 리소스 최소화)
- 스트리밍 데이터 구조체: `{시퀀스번호, 타임스탬프, 터치ID, 터치상태(Down/Move/Up), 정규화좌표(x,y), 자이로쿼터니언, 가속도벡터}`

> **v2 갱신 (6DoF)**: 컨트롤러 인식을 3DoF(회전)에서 **6DoF(위치+회전) 포즈**로 확장. 구조체에 `위치(x,y,z)` 필드가 추가되고 프로토콜 버전 2 / 패킷 72바이트가 된다. 위치 산출원(ARCore VIO 등)은 컨트롤러 앱 책임이며, 트래커 미가동 시 위치 0(3DoF 폴백). 정확한 와이어 포맷은 [NETWORK_PROTOCOL.md](NETWORK_PROTOCOL.md) 참조. 헤드트래킹은 여전히 S24+ 자체 센서 전담(5절).

## 5. 통신 안정성/예외 처리 요구사항

1. **연결 끊김 감지**: UDP 패킷 1초 이상 미수신 시 S24+ UI에 경고 표시, WebSocket 재연결 시도
2. **패킷 순서 역전 처리**: 시퀀스 번호 기준 오래된 패킷 폐기
3. **네트워크 환경 안내**: 동일 Wi-Fi 또는 S24+ 핫스팟 필수, 테스트 체크리스트에 명시
4. **지연시간 목표**: RTT 50ms 이내 (로컬 Wi-Fi/핫스팟 기준 통상 달성 가능)
5. **역할 충돌 방지**: 헤드트래킹은 S24+ 전담, S10e 자이로는 해킹 보조 연출 전담으로 명확히 분리

## 6. 2인 / 7일 작업 분배

| 일자 | 담당자 A (S24+ / 게임 로직) | 담당자 B (S10e / 통신) |
| --- | --- | --- |
| 1일차 | Cardboard Plugin 세팅, 스테레오 렌더 확인 | UDP Ping-Pong 최소 기능 검증 (필수 마감) |
| 2일차 | 카메라 리그 기반 이동/시선 상호작용 프로토타입 | 터치/자이로 캡처 및 UDP 스트리밍 |
| 3일차 | 3x3 해킹 UI 그리드 + 패턴 판정 로직 | WebSocket 서버(S24+)/클라이언트(S10e) 연결 |
| 4일차 | 입력 브릿지 통합 (UDP 파싱 → 게임 입력) | 지터 버퍼, Lerp/Slerp 보간 튜닝 |
| 5일차 | 적 AI (드론/터렛/CCTV) Unity Behavior | 재연결 로직, 핫스팟 환경 테스트 |
| 6일차 | 레벨 화이트박싱(ProBuilder), 암살 기믹 | 통합 테스트, RTT 측정/최적화 |
| 7일차 | 버그 픽스, 빌드 | 버그 픽스, 데모 리허설 |

**핵심 리스크**: 1일차 UDP Ping-Pong 검증이 실패하면 전체 일정이 흔들리므로 최우선 마감 항목으로 고정. 카드보드 렌즈 왜곡 보정도 1~2일차에 실기기로 반드시 확인 (에디터 시뮬레이션만으로는 실제 착용감 판단 불가).

## 7. 최종 패키지 체크리스트

**설치 필수**: Google Cardboard XR Plugin, URP, WebSocketSharp, NativeWebSocket, ProBuilder, DOTween, Unity Behavior

**부분 차용**: XRI (Ray/Poke Interactor의 UI 상호작용 부분만, 컨트롤러 기반 Locomotion/Grab은 미사용)

**제외됨 (v2 대비)**: Meta XR All-in-One SDK (Quest 전용이므로 카드보드 구성과 무관)

**애드온 불필요 (자체 구현)**: UDP 소켓 통신, 패킷 파서, 시퀀스 검증, Lerp/Slerp 보간, 패턴 인식 로직, 시야각 감지
