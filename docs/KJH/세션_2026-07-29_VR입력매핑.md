## 0. 결론 요약

컨트롤러가 **눈먼 터치패드**가 되면서(조이스틱·패턴 판정을 기기에서 떼어냄) **모든 해석이 MINDHEXER 몫**이 됐다.
이 세션은 그 해석 계층 — 6DoF 보정, 플릭 판정, 입력 매핑 — 을 설계했다.

핵심 결정 셋:

1. **리센터는 해킹 성공 순간에 한 번.** 조종 구간이 항상 그 이산 이벤트로 시작하므로 **두 기기의 좌표계를 맞출 필요가 없다.**
2. **컨트롤러 직결 모드.** 팀원의 페어링(WebSocket) 경로를 우회 → MINDHEXER는 UDP 수신만 하면 된다.
3. **패턴 격자 크기는 적응형.** 고정 상수가 아니라 엄지가 닿은 지점의 **가용 공간에서 유도**한다.

그리고 **코드를 읽어 확인한 막힘 3건**이 있다(§2). 셋 다 다른 세션 소유 파일이다.

## 1. 확정된 설계

### 1.1 6DoF 획득 (컨트롤러 측 — 다른 세션이 구현 완료)

ARCore VIO. `TrackedPoseDriver`가 아니라 **레거시 XR API**(`InputDevices` / `XRNode.CenterEye`)로 읽는다 —
`TrackedPoseDriver`는 Input System 패키지 소속인데 이 프로젝트는 **Active Input Handling = Old 고정**이라
(터치·자이로가 레거시 API를 쓴다) 바꾸면 조작이 통째로 죽는다.

S10e는 ARCore 인증기기다(Exynos·Qualcomm 양쪽, Depth API 포함 — 웹 확인).

### 1.2 리센터 + 좌표계 정렬

해킹 성공 순간 **세 가지**를 캡처한다:

- `P₀` 컨트롤러 위치 원점
- `Y₀` 컨트롤러 **yaw만** (기울여 든 채 성공하면 "좌우"가 대각선이 되는 것 방지)
- `H₀` 그 순간 헤드셋 yaw

```
d_local = (P_now − P₀)를 Y₀ 기준 수평 basis에 투영
d_world = yaw(H₀ − Y₀) · d_local
```

> **`FreezeControlMapping`과 같은 순간을 써야 한다.** `HackDriver.SetControlled`가 이미
> "해킹 성공 시점의 시선 기준으로 슬롯↔축 배정과 부호를 고정"한다(`HackDriver.cs:199`, 주석 §6.2).
> 리센터가 다른 순간을 쓰면 손 방향과 부품 축이 어긋난다.

### 1.3 보정 파이프라인 (5단)

| 단계 | 값 | 목적 |
|---|---|---|
| 점프 게이트 | 0.15 m/패킷 초과 시 패킷 폐기 | 추적 상실→복구 순간의 점프가 부품을 후려치는 것 방지 |
| 저역통과 | 시정수 0.05 s | VIO mm 떨림 |
| 데드존 + 히스테리시스 | 진입 1.5cm / 이탈 1.0cm | 중립 흔들림, 경계 채터링 |
| 커브 | `sign · clamp(x,0,1)^1.5` | 중심 근처 미세 조작 |
| analog 변화율 제한 | 6 /s | 지령 자체가 못 튀게 |

**부품 자체 램프가 6번째 필터로 공짜로 붙는다** — `RailSet.StepCreep`이 `MoveTowards(_vel, target, rate·dt)`로
이미 지령을 램프시킨다(`accelTime 0.08s`). `RotationPlatform`도 같은 구조. **부품 코드는 손댈 필요 없다.**

`travelScale`(최대 입력까지의 손 이동량) = **0.12 m**. 앉은 자세에서 손을 다시 안 잡고 움직이는 편도 범위가 약 15cm.

기존 부품 속도값은 이 스케일에서 이미 합리적이다:

| 부품 | 최대 입력 시 |
|---|---|
| `RailSet` (`moveSpeed 2`, 범위 ±4) | 1칸/초, 끝까지 2초 |
| `RotationPlatform` (`60°/s`, ±90°) | 끝까지 1.5초 |

### 1.4 플릭 — 미분하지 않는다

위치를 미분하면 노이즈가 증폭된다. VIO 위치 노이즈 2mm를 100Hz에서 미분하면 **0.2 m/s** — 플릭 임계와 같은 자릿수다.

대신 **시간 창 안의 변위**로 판정한다:

> 최근 **0.12초** 안에 손이 **5cm** 이상 이동 → 플릭 (회전형은 **0.15초 / 35°**)

같은 노이즈가 이 창에서는 0.03 m/s로 눌린다. 창 자체가 저역통과를 겸한다. **엣지 트리거**(임계 아래로 내려갔다 와야 재발동).

#### 플릭 복귀 문제 — 쿨다운만으로는 안 된다

플릭 후 손을 되돌리는 동작이 그대로 입력으로 들어온다. 시간 쿨다운만 두면 복귀가 느릴 때 꼬리가 새고, 빠르면 불필요하게 잠긴다.
플릭 직후 재영점도 안 된다 — 손이 끝에 있을 때 영점을 잡으면 가운데로 돌아오는 게 반대 입력이 된다.

**해법: 쿨다운의 끝을 시간이 아니라 "손이 멈춤"으로 판정하고 그 순간 재영점.**

```
플릭 발동 → 입력 무시
         → 최소 0.35초 경과 AND 속도 < 0.08 m/s 가 0.1초 지속
         → 그 지점을 새 원점으로 → 입력 재개
```

**어디로 돌아오든 그 자리가 중립이 된다** — "제자리로 정확히 돌아와야 한다"는 요구가 사라진다.
덤으로 플릭할 때마다 재영점이 걸려 **VIO 드리프트가 누적될 구간이 짧아진다.**

`FlickDir.DepthNear`/`DepthFar`는 **죽은 값**이다 — `HackDriver.FlickFor`가 Left/Right(슬롯0)·Up/Down(슬롯1)만 매핑한다.

### 1.5 입력 매핑 (PC와 1:1)

PC 입력 전체와 그 VR 대응:

| PC | VR |
|---|---|
| Space (누름/유지/뗌) | **오른쪽 절반 터치** |
| 좌/우클릭 (축) | **손 좌우 변위** — 이산 −1/+1 대신 연속 −1..1 |
| Shift + 좌/우클릭 | **손 상하 변위** (`axisV`) |
| 더블클릭 | **빠른 손 이동** (§1.4) |
| 좌클릭 (ViewEntry 사격) | **왼쪽 절반 터치** |
| 마우스 delta | **오른쪽 절반 스와이프** |
| — | **머리 회전** (VR 전용) |

컨텍스트별:

| 컨텍스트 | 손 변위 | 왼쪽 터치 | 오른쪽 터치 |
|---|---|---|---|
| `Player` | `axisH`/`axisV` + 플릭 | 조이스틱(이동) | 탭=해킹·조종해제 / 홀드=복귀(무동작) |
| `ViewEntry` | `axisH`/`axisV` | **탭=발사, 유지=연사** | 탭=해킹·조종해제 / **홀드=본체 복귀** |
| `Hacking` | — | — | **움직였으면** `strokeDir` / **안 움직였으면** 탭=취소 |

**왼쪽/오른쪽 구분이 필요한 지점은 `ViewEntry` 하나뿐이다.** PC는 사격(마우스)과 복귀(키보드)가
서로 다른 장치라 구분되지만 VR은 터치 하나뿐이다. 탭/홀드로 가르면 안 되는데, `primary`가
`wasPressedThisFrame`이라 **누르는 순간 이미 한 발 나가서** 사후 취소가 불가능하기 때문이다.

#### 해킹 중 규칙 — 무엇을 버렸는가

**버린 것: 해킹 중 홀드로 곧장 본체 복귀.** 복귀하려면 먼저 툭 쳐서 취소한 뒤 홀드한다.
구현상 **`hackHeld`를 해킹 중에 아예 안 채운다.**

- 그린 터치는 움직였으므로 뗄 때 `hack*`가 안 나가고 → **취소로 새지 않는다**
- 툭 친 터치만 `hackPressed`+`hackReleased`(합성 탭) → 취소
- `HackDriver` 수정 **불필요** — 해킹 중 `hackHeld`가 안 오니 홀드 조건이 발동할 수 없다

> PC에는 잠재 버그가 남는다. `HackDriver.cs:101`의 홀드 조건이 `_ctx.Current != ControlContext.Player`인데,
> Hacking도 Player가 아니라 **패턴 그리는 중 Space 홀드로 복귀가 돈다.** 커밋 `aa15aa6`의 명시된 의도는
> "홀드를 **빙의 중에만** 인정"이므로 `== ControlContext.ViewEntry`가 맞다. VR에는 영향 없어 미수정으로 둔다.

### 1.6 패턴 입력 — 적응형 격자

점 좌표는 `(0,1)(1,1)(0,0)(1,0)` — **점 사이 거리 = 1.0**, `hitRadius 0.16`.
`PatternInput`은 **절대 위치 기반**(휴대폰 패턴 락 방식)이고 커서가 델타를 누적한다.

**화면이 안 보이므로 절대 좌표 매핑은 무의미하다** — 엄지를 내려놓은 자리가 시작점인 **상대(플로팅)** 입력이어야 한다.
조이스틱과 같은 원리다.

**격자 배율은 터치가 내려앉는 순간 한 번 계산한다**(그리는 중엔 안 바꾼다 — 획 도중에 변하면 손이 못 따라간다):

1. 현재 커서에서 각 방향으로 가장 먼 점까지 + `hitRadius` → 필요 유닛 (최대 `1.16`)
2. 터치 지점에서 `SafeArea` 경계까지의 물리 거리 (px → DPI로 mm)
3. `배율 = min(방향별 여유 / 필요 유닛) × 0.8`
4. **등방(isotropic)** — 방향마다 다르면 대각선 획이 45°가 아니게 되어 VR에 보이는 격자와 손의 느낌이 어긋난다

**하한 ≈ 12.5mm**, 근거는 임의 상수가 아니라 **엄지 정밀도**다: 엄지 위치 재현 정밀도 ≈ 2mm,
히트 반경 `0.16` 유닛 → `0.16 × 배율 > 2mm`. 그 아래로는 히트 영역이 엄지 정밀도보다 작아 원리적으로 못 맞춘다.

S10e(2280×1080, DPI 438 → 132×63mm) 검산:

| 터치 위치 | 좁은 쪽 여유 | 배율 |
|---|---|---|
| 오른쪽 영역 한가운데 | ≈31mm | ≈19mm/점 |
| 가장자리 근처 | ≈15mm | 12.5mm (하한) |
| 구석 | ≈5mm | 하한 → **클러치로 분할** |

**떼었다 다시 잡기 = 클러치.** 델타 기반이라 손가락을 떼도 커서가 유지되고, 해킹 중엔 `hack*`를 안 보내니
상태도 안 깨진다. **엄지 도달 범위 문제가 공짜로 해결된다.**

`strokeDir`은 게임 코드를 안 건드리기 위해 **"마우스 픽셀 상당"으로 환산해서** 보낸다
(`PatternMinigame.sensitivity = 1/300`을 그대로 둔다).

### 1.7 조이스틱 (브롤스타즈식 플로팅 유지)

- **반경을 픽셀이 아니라 mm로.** 원래 `RadiusFraction × Screen.height`(픽셀)라 기기가 바뀌면 느낌이 달라진다.
  §1.6과 같이 가용 공간에서 유도하는 방식도 검토 중(구석에서 잡아도 최대 입력이 나오게).
- **`FollowOnOverflow` 켜는 것 고려** (원래 false). 화면이 안 보이면 엄지가 조금씩 밀리는데,
  꺼두면 최대 입력에 붙은 채 안 돌아온다.
- 좌/우 소유권은 **터치 시작 위치로만** 결정. 잡힌 뒤엔 반대편으로 넘어가도 그 손가락은 계속 조이스틱.
- **시각 피드백 불필요** — 화면이 안 보인다. 필요하면 VR HUD에.
- `shared`의 `FloatingJoystick`은 **픽셀 반경**을 받으므로 mm → px 환산해서 주입.

## 3. 내가 냈다가 버려진 의견 (사용자 요청으로 명시)

**같은 실수를 반복하지 않기 위해 남긴다.** 대부분 내가 코드를 안 읽고 추측했거나 요구를 잘못 이해한 것이다.

| # | 내가 주장한 것 | 왜 틀렸나 |
|---|---|---|
| 1 | "6DoF 위치가 게임플레이에 실제로 필요 없을 수도 있다. 조준은 시선 기준이니 자이로만으로 충분할 수 있다" | **완전히 틀림.** 부품(피스톤·프레스·회전판)이 각도뿐 아니라 **좌우 이동값을 요구**한다. 사용자 지적으로 정정 |
| 2 | "ARCore 대신 자이로 기울기를 좌우 이동으로 매핑하자(방법 B)" | 기각. 기울기는 이동이 아니다. 방법 A(ARCore VIO) 채택 |
| 3 | "두 기기의 좌표계가 무관한 게 6DoF의 **핵심 난점**이다" | **과장.** 조종 구간이 항상 해킹 성공이라는 이산 이벤트로 시작하므로 그때 리센터하면 끝난다. 사용자가 먼저 지적 |
| 4 | "PC에서도 우클릭이 축과 발사 양쪽에 얽히는 문제가 있다" | **사실 오류.** 발사는 **좌**클릭이고(`HexInputReader.cs:63`), 축은 `Player`·발사는 `ViewEntry`로 `switch (Context)`의 다른 분기라 겹칠 수가 없다 |
| 5 | "해킹 중엔 오른쪽=`strokeDir` 전용, **취소는 왼쪽 패널**로 옮기자" | 기각 — 조작 직관성이 떨어진다. 패널 역할이 상황마다 바뀌면 손이 헷갈린다 |
| 6 | "취소를 버리면 경로 이탈 시 **영구히 갇힌다**(`PatternState`에 Failed 없음) → 자동 리셋 또는 두 손가락 취소가 필요하다" | **"취소를 버린다"의 의미를 오해**한 데서 나온 유령 문제. 버리는 건 *해킹 중 홀드-복귀*이지 탭-취소가 아니다. 취소는 살아 있으므로 갇힘도 없다 |

| 9 | "`shared` 74파일 임포트 + `MiniWebSocketServer` 이식 + `PairingServer`로 페어링 구현" | 사용자의 "팀원 프로젝트 믿지 마라" 지적 후 폐기. **컨트롤러 직결 모드**(페어링 컴포넌트를 아예 안 붙임)로 대체 — MINDHEXER는 UDP 수신만 하면 된다 |
| 10 | Phase 1(수신·표시) / Phase 2(Map) 단계 분리 | 기각 — 자이로만으로 튜닝해봐야 정작 필요한 6DoF 조작감이 안 나온다. ARCore를 먼저 넣기로 |

## 4. 미결 — 사용자 결정이 필요하다

| # | 결정 | 막고 있는 것 |
|---|---|---|
| 1 | **속도 제어 vs 위치 제어** | `Map` 전체. 위 설계는 전부 **속도 제어** 기준이다(손 변위 = 부품 속도, 놓으면 정지). 이유는 `HexInput.axisH`가 애초에 "좌클릭(−)/우클릭(+)"이라는 속도 지령으로 정의돼 PC와 의미가 같아지기 때문. 위치 제어는 VR에서 더 직접적이나 손 도달 범위(±15cm)가 부품 행정(레일 ±4칸)보다 훨씬 짧아 **클러치를 따로 설계**해야 한다 |
| 2 | **회전 부품 — `IExternalControl`에 `ControlKind`(Linear/Rotational) 추가?** | `AxisWorld` 투영이 직선 부품엔 맞지만 회전 부품엔 안 맞는다(`RotationPlatform.AxisWorld(0)`은 **회전축**을 돌려주므로 "손을 위아래로 움직이면 회전판이 돈다"가 된다). 회전형은 **폰을 비트는 각도**로 조종해야 한다. 대안은 `is RotationPlatform` 타입 검사인데 부품이 늘 때마다 깨진다. **인터페이스는 레일 세션 소유** |
| 3 | **이동 입력을 `HexInput`에 추가?** | 막힘 §2-1. 컨트롤러에서 조이스틱을 뗀 이상 이동을 포기하지 않는 한 필드가 필요하다. `HexInputReader`·`FirstPersonPlayer`(이동 세션 파일)도 같이 바뀐다 |
| 4 | **빙의 pan/tilt를 머리로? 컨트롤러 자이로로?** | 막힘 §2-2 |

## 6. 환경 메모

- **eduroam은 단말 격리로 UDP가 막힌다**(캠퍼스 `10.x`). 노트북 모바일 핫스팟(`192.168.137.1`)이 정답.
- 노트북이 **다중 인터페이스**(eduroam `10.249.108.15` + 핫스팟 `192.168.137.1`)라 `LocalIPv4.Resolve()`가
  **기본 경로(eduroam) IP를 돌려준다.** 디스커버리를 켜면 틀린 IP를 광고하므로 **끄고** 직결로 간다.
- **Windows 방화벽** — eduroam 프로필이 `Public`. 인바운드 UDP 45710이 Unity 에디터로 들어와야 한다.
- `adb`는 `C:\Program Files\Unity\Hub\Editor\6000.5.4f1\Editor\Data\PlaybackEngines\AndroidPlayer\SDK\platform-tools\adb.exe`.
  **폰이 `unauthorized` 상태였다** — 기기에서 USB 디버깅 허용을 눌러야 한다.
