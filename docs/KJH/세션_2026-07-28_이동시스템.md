## 1. 가속 이동 (`Movement/MoveIntegrator.cs`)

즉시 속도 → **아이작식 가속/감속 램프**로 교체.

- `maxSpeed` / `acceleration` / `deceleration` / `airControl`
- 기본값: 0→최고속 0.15초, 정지 0.1초
- **왜 램프가 필요한가**: 즉시 속도면 늦게 온 입력을 보상하려고 *위치를 순간이동*시켜야 한다(눈에 띔).
  램프가 있어야 같은 보상이 *속도를 앞당기는 것*으로 나타나 안 보인다. 램프는 연출이 아니라
  지연 보상을 성립시키는 **전제**다.
- **감쇠 임펄스**(`AddBoost`) — Precog `PlayerMovement`의 `AirJumpBoost`와 같은 모델.
  일반 이동에 **덧셈**으로 얹혀 선형 감쇠. "힘을 받는" 감각의 정체가 이것이었다.
  `Output = 적분속도 + 임펄스` — 실제 이동엔 항상 `Output`을 쓴다.

## 2. 지연 보상 재설계 (설계 A′)

### 기존 설계의 문제
`InputSmoother`가 **모든 VR 입력에 일괄로 50ms 버퍼**를 걸고 있었다(해킹 터치까지).
"지연을 주고 부드러움을 사는" 거래인데, 채널마다 필요한 게 달라서 손해만 봤다:

- 이동 입력 → 가속 적분기가 이미 저역통과라 부드럽게 할 게 없음
- 이산 이벤트(터치 down/up) → 늦추면 **순수한 손해**
- 지터 → 버퍼가 아니라 패킷별 age로 잡아야 함

### A′ — 시계 동기화 없이 지터 측정 (`Infra/LatencyEstimator.cs`)

```
D   = 로컬수신시각 − 원격송신시각      (진짜 편도지연 + 두 기기 시계차)
age = D − min(D over 최근 8초)         (시계차는 상수라 상쇄 → 순수 지터)
```

- **핸드셰이크 불필요.** "두 폰 절대시각 비교 금지"(SYB NETWORK_PROTOCOL) 원칙 그대로 유지.
- 단조 덱으로 O(1) 최솟값. 상한 클램프·재연결 리셋 포함.
- **못 얻는 것**: 기저 편도 지연(모든 패킷 공통 바닥값). 시계차와 구분 불가.
  다만 상수라 조작감 영향이 작고, `MoveIntegrator.baselineCompensation` 튜닝값 하나로 보정한다.
- NTP식 오프셋 핸드셰이크(설계 A)도 검토했으나 **상하행 대칭 가정은 A도 똑같이 깔고 있어서**
  절대 정확도 이득이 없었다. A가 사는 건 패킷별 지터인데 A′가 그걸 공짜로 준다.

### InputSmoother 변경
- `InterpolationDelay` **삭제**(50ms 지연 소멸). 렌더 시점 = 현재.
- 이산/연속 분리: `TryLatest()` = 버튼·터치 즉시 / `TrySample(age)` = 연속값만 age만큼 외삽.

### 네트워크 측 계약 (미구현 — 다음 작업자용)
```csharp
NetworkHexInputSource.Active.Push(arrivalTime, remoteSendTime, sample);
```
- **양쪽 모두 단조 시계 필수.** 벽시계는 OS의 NTP 보정에 점프해서 기준선이 망가진다.
  안드로이드 `SystemClock.elapsedRealtimeNanos()`, 유니티 `Time.realtimeSinceStartupAsDouble`.
- 이산 상태 변화(이동 시작/정지)는 **중복 전송** 전제. 유실 시 다음 패킷이 덮게.
- VR 배선 시 `NetworkHexInputSource.Active.LatestAge` → `FirstPersonPlayer.InputAge`에 매 프레임 전달.

## 3. 자동 도약·등반 (`Movement/AutoTraversal.cs`)

버튼 없이 전부 자동. **판정은 엄격하게** — 후하면 오히려 불편하다.

### 발동 3중 게이트
1. **실제 낙차 있는 가장자리** — 콜라이더 경계가 아니라 `safeDrop`(0.6m) 이상 낙차 기준.
   → 붙어 있는 발판 이음매에서는 발동하지 않는다.
2. **전진 입력 유지** (`inputBuffer` 0.2초 — 선입력 손맛)
3. **yaw 원뿔 안에 도달 가능한 `ClimbLedge`**

### 높이 3단 분기
| 높이 | 처리 |
|---|---|
| ~`maxDirectUp`(1.1m) | 한 번의 도약으로 착지 |
| ~`maxMantleUp`(2.0m) | 도약 → 모서리 래치 → 당김 → 넘김 |
| 초과 / 목표 없음 | **가장자리 정지** — 바깥 속도 성분을 깎아 떨어지지 않는다 |

### 궤적
- **수평**: 진행 방향으로 치우친 2차 베지어 — 달리던 관성을 유지하다 목표로 휘어드는 대각선
- **수직**: 정점 보장 탄도. `apexY = max(출발,착지) + clearance` → 모서리를 긁지 않는다
- **속도 워핑** `u = 1−(1−x)^launchShape` → 초반 폭발 후 감속(발구름)
- **거리 반영**: `총시간 = max(탄도시간, 거리/airSpeedCap)`. 시간이 늘면 중력을 다시 풀어
  **정점·착지점은 그대로** 유지(모양 불변, 재생 시간만 조절)

### 목표 선정
```
필터: yaw 원뿔 ±coneAngle(25°) + 높이 범위 + 공간 검증
점수: yaw정렬도 − 거리 × distancePenalty(0.06)
```
yaw(수평)만 보므로 고개를 위아래로 두리번거려도 선정이 흔들리지 않는다.

## 5. 손 연출 (`Movement/MantleRig.cs`)

- 손 앵커 = 모서리 선 위, 어깨폭 간격. 모서리 끝을 잡으면 손이 몰린다.
- **손은 카메라가 아니라 월드에 고정.** 일반 FPS 뷰모델과 반대다. 고개를 돌리면 팔이 시야에서
  벗어나는데 그게 "내 손은 여전히 모서리를 잡고 있다"는 사실적 결과다.
- 래치 순간부터 **몸 위치가 손 앵커에서 역산**된다(탄도가 손을 정하는 게 아니라 반대).
- **임시 캡슐 표시** — 1인칭 팔 모델이 아직 없다. 모델이 생기면 손 앵커에 IK 타깃을 꽂으면 된다.

## 6. 화면 연출 (`Movement/MotionFeel.cs`)

동작 **종류별로** 이벤트가 갈라져 있다:

| 이벤트 | 강도 기준 | 연출 |
|---|---|---|
| `OnJumpLaunch` | 도약 높이 | 다운킥(웅크렸다 참) |
| `OnLand` | **착지 순간 수직 속도** | 침하 + 미세 흔들림 |
| `OnMantleFinish` | **고정 소량**(높이 무관) | 작은 안착 |

착지 강도가 "얼마나 높이 올라갔나"가 아니라 "얼마나 빨리 떨어지고 있었나"라서,
**높은 곳에 올라간 뒤 큰 착지 흔들림이 나오는 일이 구조적으로 없다.**
mantle 완료 시엔 `SuppressLand()`로 일반 착지 감지를 억제한다.

**당김 중 좌우 교차 롤**: `sin(진행×교차횟수) × sin(진행π)` 포락선. 교차 횟수 = 당김시간 × `swayFrequency`
→ 높은 벽일수록 여러 번 번갈아 당기는 느낌. 첫 방향은 모서리 치우침에서 결정.

**VR**: `vrPositionScale`(0.25) / `vrRollScale`(**0**). 인위적 롤은 멀미 유발 1순위라 기본 꺼둠.

## 개선해야 할 점 (다음 작업)

### A. 목표 선정 — yaw 원뿔 안에서 **순수 최근접**으로  *(사용자 지시)*
현재는 `yaw정렬도 − 거리×0.06` 혼합 점수라 정면이 우선이고 거리는 감점이다.
**원뿔은 필터로만 쓰고, 통과한 후보 중 거리 최솟값을 고르도록 바꿀 것.**
"보이는 것 중 제일 가까운 데로 뛴다"는 규칙 하나가 되어 예측 가능성이 올라간다.
→ `AutoTraversal.TryGazeJump()`의 점수식 교체. `distancePenalty` 필드는 제거하거나 0 고정.

### B. 도약 시간 최소/최대 조절값 추가  *(사용자 지시)*
현재 비행 시간은 `max(탄도시간, 거리/airSpeedCap)`으로 **하한만** 간접 통제된다.
`minFlightTime` / `maxFlightTime`을 명시 필드로 추가하고 최종 시간을 클램프할 것.
클램프로 시간이 바뀌면 **중력을 다시 풀어 정점·착지점을 유지**해야 한다
(`SolveArc`에 이미 그 재계산 로직이 있으니 같은 방식으로).
F1 패널에도 노출.

### C. 도약의 가속/감속 정도 조절값 분리  *(사용자 지시)*
현재 속도 워핑은 `launchShape` **지수 하나**로 상승·하강을 함께 처리한다.
Precog `TraversalBallistics`는 상승/하강을 나눠 썼다(`AscendShape 1.5` / `DescendShape 1.9` —
"박차고 오름" / "쿵 내리꽂힘"). **`ascendShape` / `descendShape`로 분리**하고 정점 전후로
다른 지수를 적용할 것. Precog 주석의 학습 기록도 참고: *"2.2는 과했다 — 마지막 20% 시간에
경로의 3%만 가서 끝에서 기어간다."*

> 참고: 걷기 이동의 가속/감속(`MoveIntegrator.acceleration/deceleration`)은 **이미** F1에서
> 조절 가능하다. C는 *도약 궤적*의 가속 프로파일을 말하는 것으로 해석했다.
> 만약 걷기 쪽을 의도한 것이면 이미 되어 있으니 확인만 하면 된다.

### D. 실기 검증이 안 된 것
- **VR 멀미**: `vrRollScale`을 0으로 두었다. 실기에서 켜보고 견딜 수 있는 값을 찾아야 한다.
- **지연 보상 수치**: 실제 WiFi 지터를 측정한 적이 없다. `LatencyEstimator.WindowSeconds`(8초),
  `MaxAge`(0.25초), `MoveIntegrator.maxCatchUp`(0.15초)은 전부 **추정값**이다.
- **네트워크 경로 자체가 미가동**: `NetworkHexInputSource.Map`이 null이라 VR 입력 경로는 죽어 있다.

### E. 남은 구조적 과제

## 즉시 테스트 방법

1. `HackSandbox` 씬 열기. `wall 01` 인스턴스 **스케일을 낮출 것** — 현재 0.5는 5.81m라 못 오른다.
   기즈모 선이 **초록**으로 보이면 도달 가능한 높이다(빨강이면 너무 높음).
2. Play → 벽으로 걸어가면 자동으로 잡고 올라간다.
3. **F1**로 튜닝 패널. `판정 로그` 켜면 발동/거부 사유가 콘솔에 찍힌다.
4. 확인할 것: 손 캡슐이 모서리에 정확히 붙는지 / 당김 중 좌우 갸웃 / 완료 시 큰 착지 흔들림이
   **없어야** 정상 / 목표 없는 가장자리에서 멈추는지 / 이어진 바닥에서 오발동 없는지
