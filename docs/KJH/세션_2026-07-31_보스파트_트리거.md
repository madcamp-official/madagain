## 1. 시나리오를 문서로 확정했다 (§0.4 신설)

사용자가 구술한 실제 진행 순서를 [기초_설계안 §0.4](design/기초_설계안.md)에 기록했다.
§0.2가 서사 구조라면 **§0.4가 구현 기준**이다.

```
전반부   프레스 = 문.   1·2·3 스테이지 입구를 각각 올려서 입장 → 클리어
전환점   3스테이지 클리어 후 프레스를 살짝 올리는 순간
         보스가 틈으로 머리를 쾅 박고 봉쇄 → 처음으로 내려찍어 기절 → 도주
후반부   프레스 = 무기. 역주행(3→2→1). 입구마다 막히고 막힐 때마다 내려찍음
         마지막 1스테이지 입구에서 죽임. 시작한 곳에서 끝난다(수미상관)
```

> **같은 기믹을 두 번 쓴다** — 올려서 열고(문), 내려서 찍는다(무기). 배울 것이 하나뿐이라
> 후반부에 새 기믹 없이 긴장만 오른다.

### ★ 보스 파괴 연출은 폐기됐다

**머리가 점점 찌그러지는 것을 구현하지 않는다.** "깡 하고 부딪히는 느낌", 마지막도 "깡 내려찍고
보스가 뒤로 넘어감"으로 끝낸다.

- 앞 세션 §8의 *"보스 머리 강체 변환·자세 캡처가 한 번도 실행되지 않았다 … **보스전의 첫 관문**"*
  이 항목이 **통째로 사라진다.** 가장 위험했던 미검증 항목이었다.
- `BossHeadCrush`·`BossHeadCrushPose`·`BossHeadCrushCaptureEditor`·`BossHeadRigidTool`은 용도가 없어졌다.
  **삭제하지는 않았다** — 되살릴 판단이 남아 있어서다.
- `StageEntranceFlow.headCrush`를 **의도적으로 비워 뒀다.** `Succeed()`에 `headCrush.Crush()` 호출이
  남아 있지만 null 검사로 그냥 넘어간다.
- ⚠️ §11.1의 3상태(원본→넙죽이→완전찌부) 모델 스왑 표와 **충돌한다.** 어디까지 대체되는지는
  아직 안 정했다. 양쪽에 서로를 가리키는 경고를 달아 뒀다.

## 2. 만든 것 — 코드

### 2.1 `Hackable.ignoreRange` — 거대 프레스는 어디서든 해킹

사거리 판정이 **네 곳에 흩어져 있었다.** 한 곳만 고치면 나머지가 어긋난다.

```
Hackable.WithinHackRange(distance)   ← 하나로 모음
  ├ HackDriver:318              실제 해킹 가능 판정
  ├ HackableGlitchManager:181   치지직 표시
  ├ HackableGlitchManager:171   전역 덮어쓰기(hackRangeOverride) 우회
  └ ViewmodelMotion:362         손가락 쥐기 반응
```

**조준은 그대로다** — 레이가 닿아야 잡히고 거리 판정만 빠진다(사용자 확정: "조준 제대로 됨,
추격 중이라고 특별한 것 없음"). F2 패널의 전역 사거리 덮어쓰기도 우회하므로 튜닝 중에 값이
조용히 바뀌지 않는다.

### 2.2 `BossChaseState` (신규) — 전역 추격 상태

**플레이어는 같은 입구를 두 번 지난다.** 이게 없으면 전반부에 보스가 튀어나온다.

```csharp
BossChaseState.Active      // 입구 트리거는 이게 true일 때만 발동
BossChaseState.CrushCount  // 찍은 횟수
```

- 진행 방향으로 판정하는 방법도 있으나 옆걸음·후진에서 오작동한다 → **상태 하나로 가른다.**
- 입구가 여럿인데 서로 참조하게 하면 배선이 N²로 늘어 하나만 빠져도 조용히 안 된다 → 정적.
- 씬을 다시 안 읽고 재시작하므로 `[RuntimeInitializeOnLoadMethod]`로 명시 초기화. **없으면 죽고 나서
  시작하자마자 추격 중이 된다.**

### 2.3 `BossCrushField` (신규) — 소품 파괴

부수는 게 아니라 **부모에서 떼고 Rigidbody를 붙여 날린다.** 파괴 메시가 필요 없다.

**⚠️ 대상 한정이 생명이다.** 씬 렌더러가 2만 개가 넘는다. 무제한이면 바닥·벽까지 날아가
스테이지가 무너지고 프레임이 죽는다.

- `breakableMask` — **소품 레이어만**(사용자 확정: "소품만"). **레이어가 아직 없다. 만들어야 한다.**
- 파편 콜라이더를 **`isTrigger`로 바꾼다** — 길을 뚫으러 부수는데 잔해가 새 벽이 되면 최악이다
- `maxDebris` 60 상한, 넘으면 **오래된 것부터** 치운다(새 것을 막으면 보스 앞이 안 부서져 더 어색)
- `scanInterval` 0.12초. 보스가 느려서 매 프레임 `OverlapBox`를 돌 이유가 없다
- **추격 중에만** 작동. 자기 몸은 제외
- **아직 어디에도 안 붙였다.** `MegaRobot`에 붙이고 레이어를 지정해야 동작한다

### 2.4 `StageEntranceFlow` — 진입 모드 · `Bursting` · `walkRootY`

```
Idle
 ├ [PressRaised] 프레스 t ≤ raisedThreshold(0.85) — 15%만 올려도 발동
 └ [PlayerTrigger] 트리거 통과. 단 BossChaseState.Active 일 때만
Bursting  ★신규 0.25초   (PressRaised만 거침)
 ├ 조종권 즉시 박탈 (Hackable.enabled = false)
 ├ pressActuator.Flick(0) → 프레스가 "쭉" 올라감
 └ 보스 루트를 낑김 지점으로 (u² 가속 = 들이받는 느낌)
Sealing → Wedged → Crushed / Failed
```

**"프레스가 자연스럽게 위로 쭉"의 정체는 보스 머리가 밀어올리는 것**이라, 조종권을 먼저 뺏고
스크립트가 올린다. 안 뺏으면 플레이어 입력과 강제 상승이 같은 값을 두고 싸운다(카메라 소유권
사고와 같은 구조). 프레스 상승과 머리 진입은 **같은 타이머**를 쓴다 — 따로 돌리면 머리가
프레스를 뚫거나 늦게 들어온다.

`PressRaised` 모드는 `Awake`의 `LockPress()`를 건너뛴다. **그 프레스는 플레이어가 열어야 할 문**이라
잠가 두면 전환점이 영영 발동하지 않는다.

**`walkRootY`** — 걷기 높이 복귀. §4 참조.

## 3. 만든 것 — 씬 배치 (전부 미저장)

### 3.1 체크포인트

**5개가 이미 다 있었다.** 문제는 `activateTrigger`가 전부 비어 있어 **지나가도 갱신이 안 되던 것**
(앞 세션 §7 미결). 즉 **어디서 죽든 항상 처음으로 돌아갔다.**

`Checkpoint_Stage1/2/3`이 `Stage_1/2/3` **안에** 들어가 있어 하이어라키에서 안 보였다. 밖으로 뺐다 —
체크포인트는 `IRunResettable`이 아니라 리셋 대상이 아닌데, `StageScope`는 *계층이 곧 범위*라
안에 있으면 스테이지의 일부로 오해하기 쉽다.

```
_Checkpoints
 ├ CP_0_게임시작        x = −20.0
 ├ CP_1_1스테이지       x =   6.0
 ├ CP_2_2스테이지       x = 119.5
 ├ CP_3_3스테이지       x = 233.0
 └ CP_4_보스추격직전    x = 410.5      ← 원래 이름이 `a` 였다
      └ Trigger  (각각 BoxCollider isTrigger, 4×12×34m)
```

`forwardOnly = true`라 되돌아올 때는 갱신되지 않는다 — 후반부 역주행에서 체크포인트가 거꾸로
밀리는 것을 막는다.

### 3.2 입구 4곳

**도어웨이가 아니라 대왕프레스 위치**에 놓았다. 프레스가 곧 관문이기 때문이다.
(사용자 확정: 대왕프레스 = 스테이지 입구마다 1개 + 첫 보스 등장씬 1개 = 4개)

```
_StageEntrances
 ├ Entrance_0_전환점  x = 485.7  PressRaised · startsChase   (보스 511.96 바로 앞)
 ├ Entrance_1_S3      x = 291.5  PlayerTrigger
 ├ Entrance_2_S2      x = 178.0  PlayerTrigger
 └ Entrance_3_S1      x =  64.5  PlayerTrigger               ← 마지막, 여기서 죽임
      └ WedgePoint (BossWedgePoint, 로컬 y=10)
```

역주행이 3→2→1이라 **회차(index)가 그대로 떨어진다.** `wedgeSecondsPerIndex = 0.85`의 거듭제곱이라
뒤로 갈수록 제한 시간이 짧아진다.

### 3.3 보스 높이

```
천장 y = 46.26 (거의 전 구간 일정, x=310만 21.19 — 위에 발판이 걸침)
보스   루트→머리 43.82,  루트→발 −2.84   (키 약 46.7)
→ 천장 여유 10m 기준:  루트 y = −7.56,  머리 y = 36.26
```

**보스 키가 통로 높이와 거의 같다.** 여유 10m는 임시값이고 사용자가 "추후 변경 가능"이라 했다.

### 3.4 `HeadContact`

`MegaRobot/.../Head/HeadContact` 신규. **프레스가 머리에 닿는 지점**이다.

```csharp
pressActuator.LimitT = pressActuator.TThatBrings(프레스면, headContact.position);
if (pressActuator.AtLimit) Succeed();
```

프레스가 어디까지 내려올지 정하고, **닿는 것이 곧 성공 판정**이다. 별도 명중 판정이 없다.

> 마커를 손으로 놓는 이유: 보스 `SkinnedMeshRenderer` 118개의 `localBounds`가 전부 `(3,3,3)`으로
> 통일돼 있어(컬링 문제 회피) **바운즈로는 머리 높이를 잴 수 없다.**

사용자가 위치를 조정했다. 머리 찌그러짐을 안 하므로 **위치가 고정**이다 — 원래는 단계가 오르며
같이 내려오게 할 계획이었으나 불필요해졌다.

## 4. ★ `walkRootY` — 안 되돌리면 보스가 땅속을 걷는다

걷기 높이와 낑김 높이가 **30m 가까이 다르다.**

```
걷기     루트 y = −7.56   머리 y = 36.26   ← 천장 아래
낑김     루트 y ≈ −37     머리 y ≈ 7       ← 입구 높이
Crushed  머리를 뒤로 뺌 — 원래 코드엔 y 복귀가 없었다
다음 추격 ★ 보스가 땅속에서 걸어온다
```

`TickCrushed`가 `r.forward` 방향으로만 뺐다. `walkRootY`를 추가해 `Crushed` 종료 시 복귀시킨다.
`PlayerTrigger` 입구는 `Bursting`을 안 거치므로 `Begin()`에서도 기억한다.
인스펙터를 비우면(NaN) 사이클 직전 높이를 자동으로 쓰고, 값이 있으면 확정값. **지금 4곳 다 −7.56.**

> 낑길 때 아랫도리가 파묻히는 것은 **설계상 괜찮다** — §0.2에 *"추격 중=좁아서 상체만"* 이라고
> 적혀 있다. 내가 처음에 이걸 문제로 착각해 "발을 바닥에 붙여야 한다"고 잘못 말했다.

## 9. 이번에 겪은 함정

**유니티의 "가짜 null"에 두 번 걸렸다.** 리플렉션으로 얻은 필드 값을 `!= null`로 비교하면
`object` 비교라 유니티가 오버로드한 `==`을 안 탄다 — 미할당 `Collider` 필드가 "값이 있다"로 판정돼
체크포인트 배선이 **0개**로 끝났다. `as UnityEngine.Object`로 캐스팅한 뒤 비교해야 걸린다.
(`DangerZoneVisual`에서 겪은 것과 같은 함정이다.)

**측정이 오염될 수 있다.** 천장을 재려고 위로 레이캐스트했더니 `ground corner`(바닥 단차)가
3m에서 잡혔다. 시작 높이를 올려(y=20) 다시 재야 실제 천장 46.26이 나왔다. **한 지점만 재고
결론 내지 말 것.**

**내가 틀린 것 하나**: 보스 발이 바닥 아래에 있는 것을 문제로 보고 "루트를 올려 발을 붙여야
한다"고 했는데, §0.2에 이미 *"추격 중=좁아서 상체만"* 이라고 적혀 있었다. **설계 문서를 먼저
확인했으면 안 틀렸다.**
