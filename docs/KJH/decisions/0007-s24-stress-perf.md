# ADR-0007 — S24+ 실기 성능 측정 (최악 시나리오 스트레스 씬)

상태: 1차 측정 완료. **최적화는 게임 완성 후로 연기** (사용자 결정, 2026-07-29)
날짜: 2026-07-29
기기: **SM-S926N (Galaxy S24+), Android 16** / Cardboard XR, 개발 빌드
관련: ADR-0006(통합 리그)

---

## 목적

"리깅된 보스가 마구 움직이고 demoscene을 얹고 경비병이 죽어나가는 엉망진창 최악 시나리오"를
만들어 실기 한계를 재는 것. **최적화 대상이 아니라 측정 도구**다.

## 측정 도구

| 도구 | 내용 |
|---|---|
| `VrStatsHud` | fps·평균ms·스파이크·최악·경과시간 + 렌더러/스킨/애니메이터/정점 수. **월드 공간 텍스트**(스테레오에서 화면 오버레이는 양안에 한 번만 그려져 어긋난다) + logcat 시계열 |
| `StressDirector` | 도시 additive 로드 + 보스 N기(회전·애니 무작위 전환) + 경비병 웨이브(스폰→일괄 `Destruct`) |
| 씬 | `Assets/_Project/Scenes/StressLab.unity` |

**경과 시간을 반드시 함께 남긴다** — 발열 스로틀링은 순간값이 아니라 시계열로만 드러난다.

**씬 규모 집계는 드물게(15초)만 한다** — `FindObjectsByType`이 수천 오브젝트에서 그 자체로
스파이크라, 매 프레임 세면 **측정 행위가 측정 대상을 오염시킨다**.

## 1차 측정에서 나온 것 — 성능이 아니라 **버그**였다

첫 측정은 60fps → 17fps로 무너졌고 렌더러가 `2,808 → 12,295`로 **끝없이 증가**했다.
발열 스로틀링처럼 보였지만 아니었다.

### 결정적 단서

**정점 수는 113,000k에서 평평한데 렌더러 수만 계속 늘었다.** 정점 없는 렌더러가 매 프레임
생긴다는 뜻 — 그리고 그건 매 프레임 `ArgumentNullException`을 던지던 `ControlTether`와 같은 곳이었다.

### 원인 — 결함 2개가 아니라 1개

```csharp
// 문제의 구조
var go = GameObject.CreatePrimitive(PrimitiveType.Cube);   // ① 먼저 만들고
_mat = new Material(Shader.Find("Universal Render Pipeline/Unlit"));  // ② 여기서 예외
_bar = go.transform;                                        // ③ 도달 못 함
```

셰이더가 빌드에 없으면 ②에서 던지고 `_bar`가 **끝내 할당되지 않는다** → 다음 프레임에 또
`EnsureBar()`가 돌아 ①을 반복 → **프레임당 큐브 하나씩 누수**.

**셰이더 누락 하나가 예외와 누수 양쪽의 원인이었다.**

### 고친 것

- **셰이더를 먼저 찾고**, 실패하면 오브젝트를 만들지 않는다. 실패 상태를 기억해 재시도도 안 한다
- 런타임 `Shader.Find` 전수 조사 → Always Included Shaders에 추가:
  `Universal Render Pipeline/Unlit`(ControlTether·ControlAxisGizmo·TurretGun),
  `MINDHEXER/HackGlitch`(HackableGlitchManager), `MINDHEXER/ViewConeMask`(ViewConeMask)

> **교훈**: `Shader.Find`는 에디터에선 항상 성공하고 빌드에서만 실패한다. 런타임에 쓰는 셰이더는
> 전부 Always Included에 넣어야 한다. 그리고 **자원을 확보하기 전에 실패할 수 있는 호출을
> 먼저 하라** — 순서만 바꿔도 누수가 사라진다.

> **내 판단 오류**: 렌더러 증가를 보고 "파편 누수"라고 단정했으나, `GuardDestruction`의
> `life: 8`은 정상이었다. 정점 수가 평평하다는 것을 보고서야 원인을 제대로 찾았다.
> 수치가 오르는 것을 보고 원인을 추측하지 말 것.

## 수정 후 — 진짜 성능 수치

렌더러가 **1,957~2,043에서 안정**(웨이브 진폭만), 예외 0건.

| 시점 | 씬 내용 | fps |
|---|---|---|
| t=5s | 보스 6기만 (렌더러 7, 정점 **19k**) | **56.5** |
| t=20s | 도시 로드 완료 (렌더러 1,951, 정점 **112,616k**) | 52.5 |
| t=50s | | 48.1 |
| t=81s | | 34.1 |
| t=142s | 정상 상태 | **35.0** |

### 해석

- **보스·경비병은 거의 무죄.** 6기 다 띄워도 정점 19k, 56fps
- **도시가 들어오는 순간 정점이 5,900배**(19k → 1억 1,261만)
- 렌더러당 평균 **5만 8천 정점** — 모바일 VR에서 물체 하나가 5만이면 이미 과하다. 그게 2천 개,
  스테레오라 전부 두 번
- 렌더러가 안정된 뒤에도 52 → 35로 하락 후 평평 → **발열 스로틀링으로 보임**(미확정)

VR 목표 60fps 대비 **약 40% 부족**.

## 확인된 컬링 상태

| 항목 | 상태 |
|---|---|
| 프러스텀 컬링(시야 밖) | 동작 — Unity 기본, 끌 수 없음 |
| **오클루전 컬링**(가려진 것) | **미베이크** — `m_OcclusionCullingData: {fileID: 0}` (StressLab·DemoScene 둘 다) |
| **LOD** | **DemoScene에 `LODGroup` 0개** — 거리 무관 항상 원본 밀도 |

즉 지금은 "보이는 것만"이 아니라 **"카메라 앞쪽 전부"** 를 그린다. 밀집한 도시에서 앞 건물에
완전히 가려진 뒤쪽 건물도 정점을 처리하고, 100m 밖 건물도 1m 앞과 같은 밀도로 그린다.

## 다음에 할 것 (게임 완성 후)

병목 **종류부터** 가른 뒤 대책을 고른다. 순서를 지키지 않으면 엉뚱한 곳을 깎게 된다.

1. **`renderScale` 0.5로 낮춰 재기** — 프레임이 크게 오르면 픽셀(래스터라이즈) 병목,
   거의 안 오르면 정점·드로우콜 병목. **한 줄이고 즉시 답이 나오는 판별 실험**
2. **Unity Profiler 연결** — 개발 빌드라 바로 붙는다. 드로우콜·SetPass·SRP Batcher·인스턴싱 여부
3. **`StressDirector`에 부하별 on/off 토글** — 도시만·보스만 켜고 각각 재 기여도 분리
4. 정점 병목이면 → **오클루전 베이크 + LOD**. 픽셀 병목이면 → 렌더스케일·셰이더 복잡도
5. **스로틀링 확인** — 5~10분 더 돌려 하락이 멈추는 지점 측정
