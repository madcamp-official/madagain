# ADR-0004 — 자동 도약의 방향 판정: 원뿔 축을 무엇으로 둘 것인가

> 상태: **확정** (2026-07-28) · 관련 코드: `View/Movement/AutoTraversal.cs` `TryGazeJump()`
> 관련 문서: [세션_2026-07-28_이동시스템.md](../세션_2026-07-28_이동시스템.md) · [세션_2026-07-28_이동판정개선.md](../세션_2026-07-28_이동판정개선.md)

## 배경

버튼 없는 자동 도약이라 **"언제 어디로 뛸지"를 시스템이 정해야 한다.** 후보는 씬의
`ClimbLedge` 마커 전부이고, 그중 하나를 고르는 필터가 **원뿔**이다.

원뿔의 **축**을 무엇으로 둘 것인가 — 이게 세 번 바뀌었고, 매번 실기에서 문제가 드러났다.
같은 실수를 반복하지 않으려고 경위를 남긴다.

이 판정은 단순한 "목표 선택"이 아니다. **낙하 보호(EdgeStop)와 한 몸**이다:

```csharp
if (bottomless || drop > safeDrop)
{
    if (ready && TryGazeJump()) return;          // ← 도약이 성립하면 여기서 끝
    if (bottomless || drop > maxSafeFall) EdgeStop(dir);   // ← 못 뛰면 막는다
    return;
}
```

`TryGazeJump()`가 true를 반환하면 **낙하 보호를 건너뛴다.** 그래서 원뿔이 과하게 허용하면
"보호가 꺼진 채 아무 데도 안 뛰는" 구멍이 생긴다. 이게 3차 실패의 정체였다.

---

## 시도 1 — 축 = 시선(look)

**의도**: 사용자 요구가 "바라보는 화면 안 오브젝트 중 가장 가까운 것으로 뛴다"였다.

**실패**: 옆걸음·대각선. 가장자리 감지(`DropDepth`)와 궤적 출발 접선은 **이동 방향** 기준인데
목표 선정만 시선 기준이라, 앞을 보면서 옆으로 달려 가장자리에 가면 목표가 원뿔 밖으로 빠졌다.
→ `TryGazeJump` false → 그냥 떨어짐.

## 시도 2 — 축 = 시선 OR 이동 방향

**의도**: 시도 1의 사각지대를 메운다. 둘 중 하나만 통과하면 인정.

```csharp
if (Dot(run, toDir) < cosCone && Dot(look, toDir) < cosCone) continue;
```

**실패**: 정확히 반대 방향으로 과하게 허용됐다.

> **앞에 후보를 둔 채 S로 뒤로 걸으면, 그 앞 후보가 `look`으로 통과한다.**
> `TryGazeJump`가 true를 반환 → `return` → **뒤쪽(실제로 떠나는 방향)은 아무 판단도 없이
> `EdgeStop`만 건너뛴 채 낭떠러지로 걸어나간다.**

옆걸음(A/D)도 동일하다. 앞을 보면서 옆으로 나가면 앞 후보가 승인해버려 옆 낙하 보호가 뚫린다.

시도 1의 증상("옆으로 가면 떨어짐")과 시도 2의 증상("뒤·옆으로 가면 떨어짐")이 **표면상 비슷해서
같은 문제로 착각하기 쉽다.** 원인은 정반대다 — 하나는 너무 좁아서, 하나는 너무 넓어서다.

## 시도 3(확정) — 축 = 이동 방향 하나

**원칙**: **발판을 떠나는 방향은 이동 방향이다. 그러니 목표도 그 방향에 있어야 한다.**

```csharp
Vector3 run = _lastMoveDir; run.y = 0f;
if (run.sqrMagnitude < 1e-4f) return false;   // 떠날 방향이 없으면 도약도 없다
run.Normalize();
...
if (Vector3.Dot(run, toDir) < cosCone) { Rej(ledge, "원뿔 밖(이동 방향)"); continue; }
```

- 뒤로 가면 **뒤쪽** 목표만, 옆으로 가면 **옆쪽** 목표만 인정한다.
- 그 방향에 목표가 없으면 `TryGazeJump`가 false → `EdgeStop`이 정상 작동한다.
- **낙하 보호와 도약 판정이 같은 축을 쓴다** — 이게 시도 1·2가 못 지킨 불변식이다.

수평(yaw)만 본다. 고개를 들든 숙이든 선정이 흔들리지 않고, 높이는 `dh` 조건이 따로 거른다.

## 결과

**"시선 도약"이라는 이름과 달리 시선은 선정에 전혀 관여하지 않는다.**

실은 시도 2 시점에도 시선의 역할은 이미 **승인 게이트뿐**이었다 — 선정 규칙은 "원뿔 통과 중
최근접"이라 시선이 우선순위를 정하지 않았다. 그 유일한 역할이 버그의 원인이었으므로 제거해도
잃는 기능이 없다.

**포기한 것**: "멀리 있는 발판을 쳐다보면서 옆으로 걸어 나가 그쪽으로 뛰기". 이건 애초에
의도한 조작이 아니었고, 바로 그 경로가 낙하 보호를 뚫었다.

**검토했으나 채택하지 않은 안 (B)**: 이동 방향 원뿔을 필수로 하고, 그 안에서 시선에 가까운 것을
우선 선정. 규칙이 둘이 되어 "왜 저기로 뛰었지"가 다시 생긴다. 최근접 하나로 두는 편이 예측된다.

## 미결 — 함께 검토했으나 아직 안 정한 것

**목표가 없을 때의 낙하 규칙.** 지금은 낙차가 `maxSafeFall`(2.5m) 이하면 **일부러 떨어뜨린다**
("아래층으로 내려가는 유일한 길"이라는 전임 세션의 의도).

```csharp
if (bottomless || drop > maxSafeFall) EdgeStop(dir);   // 그보다 얕으면 그냥 떨어진다
```

대안: "목표가 있을 때만 내려가고, 아니면 항상 멈춤". 그러면 아래층으로 가려면 반드시
`ClimbLedge`가 있어야 하므로 **레벨 디자인이 이동 가능 경로를 완전히 통제**하게 된다.
퍼즐 게임이므로 그쪽이 맞을 수 있으나, 모든 하강 지점에 마커를 붙여야 하는 비용이 있다.

→ **사용자 판단 대기.**

## 교훈

1. **판정과 안전장치가 다른 기준을 쓰면 반드시 구멍이 난다.** 도약 승인(`TryGazeJump`)과
   낙하 보호(`EdgeStop`)가 같은 방향 축을 공유하도록 강제한 것이 이번 수정의 본질이다.
2. **조건을 OR로 넓혀 사각지대를 메우면, 반대편에 과잉 허용이 생긴다.** 축 자체를 바꿔야 할
   문제를 조건 추가로 덮으려 한 것이 시도 2의 실수였다.
3. 증상이 비슷해도 원인이 정반대일 수 있다. "떨어진다"는 같은 보고가 시도 1에서는 **너무 좁아서**,
   시도 2에서는 **너무 넓어서** 나왔다.
