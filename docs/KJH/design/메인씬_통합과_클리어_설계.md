## 0. 왜 통합했나 — 최적화가 아니라 전제 조건

`보스전_설계.md` 2막은 "왔던 길을 **역순으로** 도주하며 스테이지 입구 4곳에서 프레스로 찍는다"이다.
스테이지가 별도 씬이면 보스가 스테이지를 **가로질러 쫓아올 수 없다.** 즉 통합은 성능 항목이 아니라
보스전이 성립하기 위한 전제다. 거리 컬링·Static·텍스처 압축은 통합의 부수 효과다.

## 1. 통합 기록 (완료)

### 1.1 배치 규칙 — 도어웨이가 이미 규격화돼 있었다

실측: 모든 스테이지가 아래로 동일했다.

| | 위치 | yaw |
|---|---|---|
| `_Doorway` (들어오는 쪽) | (0, 0, 0) | 0 |
| `_Doorway (1)` (나가는 쪽) | (113.5, 0, 0) | 0 |

→ **X로 113.5씩 밀면 정확히 맞물린다.** 회전·오프셋 보정이 필요 없다.

```
Stage_1  [0.0] ────────── [113.5]
Stage_2            [113.5] ────────── [227.0]
Stage_3                       [227.0] ────────── [340.5]
```

- `Stage_0`은 테스트용이라 **제외**했다.
- `WayIN`·`Boss`는 `_Doorway`가 없어 사용자가 직접 연결했다.

### 1.2 인프라 중복 제거

스테이지마다 `[GameBoot]`·`Main Camera`·`Directional Light`·`[GreyscaleTest]`·`[TestLights]`·`[OneBit]`이
들어 있었다. 그대로 합치면 3벌이 겹친다. **첫 등장만 채택**하고 나머지는 버렸다.

| | 지오메트리 | 인프라 |
|---|---|---|
| Stage_1 | 25 | 5개 채택 |
| Stage_2 | 34 | `[OneBit]` 채택, 5개 버림 |
| Stage_3 | 54 | 6개 전부 버림 |

> ⚠️ 조명(`Directional Light`·`[TestLights]`)을 **Stage_1 것으로 통일**했다. 스테이지마다 조명을
> 다르게 잡아 뒀다면 이 선택이 틀린 것이므로 다시 해야 한다.

### 1.3 이음새 중복 제거 — 390개

두 이음새에서 앞 스테이지의 `_Doorway (1)`과 뒤 스테이지의 `_Doorway`가 **완전히 같은 자리에** 있었다.

판정은 **메시 + 월드 위치·회전·스케일이 전부 일치**할 때만(느슨하게 잡으면 안 겹치는 것까지 지운다).

| 이음새 | 앞 | 뒤 | 삭제 |
|---|---|---|---|
| x=113.5 | 201 | 195 | **195** |
| x=227.0 | 201 | 195 | **195** |

뒤쪽에서 안 겹치는 조각이 **0개**였다 — 들어오는 문이 나가는 문에 완전히 포함된다. 나가는 문이
6조각 더 크고, 그 6개는 앞 스테이지에 남아 있다.

### 1.4 현재 수치

```
루트 10개 (Stage_1/2/3 + 인프라 6 + [작업용 조명])
렌더러 20,021   트랜스폼 21,186
```

`최적화_후보.md`가 Stage1 단독을 2,088 렌더러로 기록했는데, 통합본은 그 **10배**다.
거리 컬링·Static·오클루전 베이크가 이 문서의 전제로 바뀌었다.

### 1.5 되돌리기 · 정본 문제

- **원본 `Stage_1~3.unity`는 그대로 남아 있다.** `MainScene.unity`만 지우면 원상복구된다.
- 그래서 지금 **정본이 둘**이다. 앞으로 스테이지를 고칠 때 어느 쪽을 고칠지 정해야 하고,
  이건 forDev 동기화 방식(`ADR-0003`)에도 직접 영향을 준다. → §4 미결

## 2. 클리어 가능하게 만들기

### 2.1 시작 지점 5곳 — 리셋 범위와 같은 물건이다

필요한 지점:

| # | 지점 | 범위 |
|---|---|---|
| 1 | 게임 시작 | — |
| 2 | 1스테이지 시작 | Stage_1 |
| 3 | 2스테이지 시작 | Stage_2 |
| 4 | 3스테이지 시작 | Stage_3 |
| 5 | 보스 추격 직전 | 추격 |

이건 `사망_부활_연출_설계.md` §4가 이미 설계해 둔 **`Checkpoint` + `StageScope`** 와 같은 물건이다.
따로 만들지 않는다.

```
Stage_N  (StageScope, index = N)
 ├ Checkpoint        부활·시작 지점 — 위치 + 바라볼 방향(yaw)
 └ ... 이 밑의 IRunResettable만 초기화된다
```

- 게임 시작·보스 추격 직전은 스테이지에 속하지 않으므로 **별도 루트**에 둔다.
- `DeathSequence.OnResetPoint`(암전이 완전히 덮인 순간)에서 "해당 범위 리셋 + 체크포인트로 이동"을
  수행한다. 훅은 이미 뚫려 있고 **구독자만 없다.**
- 방향(yaw)도 저장해야 한다. 부활 직후 기상 연출이 yaw를 유지하도록 만들어져 있으므로
  (`WakeUpSequence`가 현재 yaw를 읽어 그대로 둔다) 체크포인트가 정한 방향이 그대로 유지된다.

**이걸 제일 먼저 해야 한다** — 나머지 다섯 작업을 테스트하려면 그 스테이지에서 바로 시작할 수 있어야 한다.

### 2.2 피스톤 탑승 — **새 코드가 필요 없다**

이미 다 있다.

- `TelescopingActuator.Apply()`가 매 프레임 head의 이동량만큼 `_headPlatform.Carry(delta)`를 부른다.
  `_headPlatform`은 **head에 붙은 `RailPlatform`을 런타임에 찾아온 것**이다.
- `WalkSurfaceCollider`가 Anchor~Head 사이를 **평평한 박스 하나**로 덮는다. 시각 파츠(막대 여러 개)와
  무관하게 매끈한 발판이 되고, Head 쪽 면이 Head를 따라간다.

→ **배선만**: 피스톤 `head`에 `RailPlatform` 추가 + `WalkSurfaceCollider`에 BoxCollider 연결.

> `RailPlatform.Carry`는 계층 부모 지정이 아니라 **델타를 더하는** 방식이다. `CharacterController`와
> 싸우지 않기 위해서다(레일 세트가 쓰는 것과 같은 장치).

### 2.3 레일캐리어 교체 — 지금 상태가 틀려 있다

실측한 문제:

| | 현재 | 문제 |
|---|---|---|
| 배치 | `RailCarrier` 프리팹 **147개**(전 씬) | 조각 하나하나가 **개별 Hackable** |
| 조종 축 | 월드 **X + Z 2축** | 코드 주석에 "테스트 설정"이라 명시. 레일 방향(로컬 Y)과 무관 |
| 플릭 | `flickDistance 50` > `travelMax 6` | 한 번에 무조건 끝까지 |
| `RailSet` | **0개** | 칸 스냅·라이더 운반·범위 표시가 전부 없음 |

목표 구조(`RailSet` 문서가 정한 것):

```
[레일세트]  ← Hackable + RailSet   ★ 이 트랜스폼이 움직인다(레일도 함께 밀린다)
 ├ Rails/   ← 조각들. 렌더러만, 콜라이더 없음
 └ Riders/  ← 터렛·발판 (RailPlatform 붙여야 실려 간다)
```

- 가동범위는 **씬 뷰에서 양 끝 핸들을 끌어** 잡는다(`RailSetEditor`).
- 플릭 간격은 `stepTarget`이 정하고, 범위를 그 간격으로 쪼개 눈금을 만든다. 끝 자투리는
  `tailMergeRatio`로 직전 칸에 합친다.
- 실측 규격: 두 줄이 한 칸, **칸 간격 9.75**, 8칸, 전체 길이 68.25.

> ⚠️ **정점 문제는 별건이다.** 레일 조각 하나가 정점 12,430(삼각형 9,225)이라 147개면 183만 정점이다.
> 구조 교체와 정점 감축은 분리해서 진행한다 — 섞으면 무엇 때문에 좋아졌는지 알 수 없다.

### 2.4 점프·낙하 거리 조정

**실측이 먼저다.** 지금 값이 맞는지 틀린지 알 근거가 없다.

1. 통합 씬에서 **실제로 건너야 하는 간격·낙차**를 잰다(발판 사이, 레일 위, 피스톤 위).
2. 그 최댓값이 현재 점프로 닿는지 본다.
3. 안 닿으면 점프를 올리는 게 아니라 **간격을 줄이는 쪽을 먼저** 검토한다 — 점프를 키우면
   다른 스테이지의 난이도가 전부 흔들린다.

### 2.5 경비병 이동 루트

`GuardPatrol` 웨이포인트로 잡는다. `GuardPatrolEditor`에 **N개 일괄 생성** 도구가 이미 있고,
`GuardPatrolPath (경비병 이름)` 빈 오브젝트 밑에 만들어 준다.

> 회전은 `GuardTurnStep`이 맡는다(정지 후 발을 떼며 도는 연출). 웨이포인트 간격이 너무 촘촘하면
> 회전이 끝나기 전에 다음 목표가 와서 어색해진다.

### 2.6 해킹 거리 튜닝

| 값 | 현재 | 뜻 |
|---|---|---|
| `Hackable.hackRange` | 15 | 실제 해킹 가능 거리(대상별) |
| `HackDriver.aimMaxRange` | 100 | 조준 레이 길이. **hackRange보다 넉넉해야** 사거리 밖에서도 조준은 되고 치지직 밀도로 "아직 멀다"가 읽힌다 |

- **초거대 유압프레스는 사거리 제한을 두지 않는다**(확정). 보스가 낑긴 동안 멀리서도 찍어야 한다.
  프리팹 값으로 큰 수를 넣는다.
- 나머지는 스테이지에서 실제로 서는 위치에서 재서 잡는다.

## 3. 순서

1. **시작 지점 5곳** — 나머지를 테스트하려면 이것부터. 리셋 배선(`OnResetPoint` 구독)도 같이
2. **피스톤 탑승 배선** — 새 코드 없음, 제일 싸다
3. **레일 교체** — 구조만. 정점 감축은 뒤로
4. **점프·해킹 거리** — 실측 후 튜닝
5. **경비병 루트**

보스전(초거대 프레스·낑김·팔 봉쇄)은 이 다섯이 끝나 **한 번 클리어되는 상태**가 된 뒤에 얹는다.
