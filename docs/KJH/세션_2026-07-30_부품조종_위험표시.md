## 0. 결론 요약

지시받은 것은 "피스톤·프레스·레일 작업"이었지만, **본체는 카메라 소유권 사고**였다.
`ViewmodelMotion`이 메인 카메라를 뷰모델로 오인해 **PC에선 시점 회전이, VR에선 눈높이가 죽어 있었다.**
증상이 원인과 전혀 안 닮아서(마우스를 움직여도 화면이 안 돎 / 머리는 도는데 위치가 죽음) 찾는 데 오래 걸렸다.

그 외 완료: 액추에이터 조종 전체, 터렛 재분류(빙의→외부 조종), 경비병 감지 부채꼴, 흑백 노이즈 위험 표시,
마일스톤 양자화. **레일 세트는 수치 미확정으로 의도적 보류**(§7).

## 1. ★ 카메라 소유권 — 근본 재설계 (가장 중요)

### 무슨 일이었나

`ViewmodelMotion`(1인칭 팔 흔들림)이 흔들 대상을 못 찾으면 `transform.GetChild(0)`로 **아무거나** 집었다.
이 컴포넌트는 `[PlayerBody]`에 붙는데 그 첫 자식이 **Main Camera**였다. 그래서 매 LateUpdate마다

```csharp
vmRoot.localPosition = basePos + pos;
vmRoot.localRotation = baseRot * Euler(rot);   // 절대 대입
```

로 카메라의 위치·회전을 통째로 덮어썼다.

**PC와 VR에서 증상이 달랐던 이유**: VR의 `TrackedPoseDriver`는 `UpdateAndBeforeRender`라 **렌더 직전에
회전을 다시 쓴다** → 회전은 살아남고 위치만 죽었다. PC는 그 재적용이 없어 회전이 통째로 죽었다.
**버그 하나가 두 플랫폼에서 다른 얼굴로 나타났다.**

### 진단 방법 (재발 시 이대로)

`MouseLook`의 내부 각도를 강제로 넣고 트랜스폼과 비교했다.

```
_yaw = 123, _pitch = 5   ← 입력 누적은 정상
cam localEuler = (0.07, 0, 0)   ← 반영 안 됨 → 다른 작성자가 덮어쓰고 있다
```

> ⚠️ MCP로 Play 중 측정할 때 **에디터가 백그라운드면 게임 루프가 멈춘다**(`runInBackground=False`).
> `frameCount`가 2에서 고정되면 그 상황이다. `Application.runInBackground = true`를 런타임에 켜고 재라.

### 최종 리그 구조

```
[PlayerBody]       CharacterController                    ← 월드 위치
 └ [Head]          MouseLook(PC) / TrackedPoseDriver(VR)   ← 시점 회전 · VR 눈높이(VrTuning)
    └ Main Camera  MotionFeel(연출 오프셋·롤) · HackDriver ← 연출
       └ Viewmodel ViewmodelMotion                         ← 팔 (있을 때만)
```

**★ 순서가 중요하다 — 연출이 시점보다 아래여야 한다.** 롤은 *시선 축*을 돌아야 하는데, 연출을 시점
*위*에 두면 "몸의 앞 축"을 돌아 옆을 볼수록 피치로 변질된다. 실측:

```
yaw 90° + roll 20°
  연출이 위(잘못): fwd = (0.94, 0.34, 0.00)   ← 시선이 19° 들림
  연출이 아래(정상): fwd = (1.00, 0.00, 0.00)   up = (0, 0.94, 0.34)
  두 회전 차이 28.2°
```

> **중간에 내가 한 번 틀렸다.** 처음엔 `[CamRig]`를 시점 **위**에 뒀다가 이 회귀를 만들었다.
> 실측으로 잡아서 순서를 뒤집었다. 다시 만질 때 이 순서를 되돌리지 말 것.

### 트랜스폼 속성별 소유자 (하나씩만)

| 속성 | 소유자 |
|---|---|
| `[PlayerBody]` 위치 | CharacterController |
| `[Head]` 로컬회전 | MouseLook(PC) / TrackedPoseDriver(VR) |
| `[Head]` 로컬위치 | VrTuning(VR 눈높이). PC는 0 |
| `Main Camera` 위치·로컬회전 | MotionFeel |
| `Viewmodel` | ViewmodelMotion |

**원칙 4개** — 어기면 같은 사고가 또 난다.
1. 한 트랜스폼 속성에는 소유자가 하나.
2. 소유자만 절대 대입. 위에 얹는 연출은 **델타**(되돌리고 다시 더함 — `MotionFeel` 방식).
3. 대상을 못 찾으면 **아무것도 하지 않는다.** 추측해서 잡지 않는다.
4. VR에선 BeforeRender가 최종 진실. 이를 방해하는 LateUpdate 작성자를 두지 않는다.

### 부수 효과

- **VR에서도 롤 연출이 가능해졌다.** 전에는 롤을 합성해 주는 게 `MouseLook`뿐이라 VR엔 아예 없었다.
  (멀미 때문에 `vrRollScale = 0` 기본값은 유지 — 이제는 '없는 것'이 아니라 '꺼둔 것'이다.)
- `MotionFeel.ownsRotation` 필드로 명시 지정한다. **자동 판정은 위험하다** — "카메라가 안 붙어 있으면
  리그"로 판정했더니 `ViewmodelStudio`에선 `MotionFeel`이 **몸**에 직접 붙어 있어 몸을 굴릴 뻔했다.
- `GameBoot.AuditCameraOwnership()`이 Play 직후 소유권을 검사해 `LogError`. VR 실기에선 콘솔을 못 보므로
  `VrStatsHud`에 `look:tpd|mouse|BOTH!|NONE!` 한 항목을 넣었다.

### 뷰모델 루트 판정 통일 — `ViewmodelRoot.cs` (신규)

`ViewmodelMotion`·`ViewmodelCamera`·`PosePlayer`가 각자 찾고 **셋 다 같은 폴백 결함**을 갖고 있었다.
판정을 한 곳으로 모았다.

- 이름으로만 찾는다. **순서 기반 폴백 없음.**
- **카메라를 품은 대상은 거부**한다(마지막 방어선).
- 못 찾으면 `null` → 호출자는 아무것도 하지 않는다.
- `ViewmodelMotionBoot`의 자동 부착을 **조건부**로 바꿨다 — 뷰모델이 없는 씬에선 컴포넌트가 안 생긴다.

**`ViewmodelStudio`에서 부수 효과 확인**: 카메라 자식이 `Viewmodel`과 `[ViewmodelCam]` **둘**이라
예전 `GetChild(0)` 폴백은 순서에 따라 오버레이 카메라를 팔로 집을 수 있었다. 그 경로도 막혔다.

### 같이 발견해 고친 별개 버그

- **`ViewmodelMotion`의 시선 스웨이가 한 번도 안 걸렸다.** `[PlayerBody]`는 회전하지 않는데(rotation=identity
  고정) 자기 트랜스폼 각도를 읽고 있었다 → 항상 0. `fpp.view`의 **월드** 각도를 읽게 고쳤다.
- **`RailPlatform`·`RotationPlatform`의 지하철 스웨이가 한 번도 안 걸렸다.**
  `cc.TryGetComponent(out MotionFeel)`로 찾는데 `cc`는 `[PlayerBody]`이고 `MotionFeel`은 카메라 쪽에 있다.
  `GetComponentInChildren`으로 고쳤다.
- `FirstPersonPlayer.Instance` 추가 — 리그가 런타임 생성이라 인스펙터로 참조를 물릴 수 없다.

## 2. 피스톤 · 유압프레스 — 조종 완성

### `ActuatorControl.cs` (신규)

`TelescopingActuator`가 "어떻게 늘어나는가", 이쪽이 "무엇이 얼마나 늘리는가". 종류 enum을 두지 않았다 —
피스톤·프레스 차이는 조작법이 아니라 구동 값뿐이라 부품이 늘어도 이 파일은 안 바뀐다.

- 홀드 = 살살, 플릭 = 끝에서 끝. **좌클릭 = 신장**으로 고정.
- **`IExternalControl.ScreenRelativeSign` 신설.** 축의 두 끝이 대칭이 아닌 물체는 화면 기준 부호 보정을
  받으면 안 된다 — 물체 뒤로 돌아가는 순간 좌/우가 뒤집혀 조작이 예측 불가능해진다.
  레일·갠트리·회전판은 `true`, 액추에이터는 `false`. `HackDriver.FreezeControlMapping`에서 분기.
- **액추에이터는 자식에서 찾는다.** `TelescopingActuator`는 파츠 참조 때문에 모델 프리팹 안에 있어야 하고,
  `ActuatorControl`은 `Hackable`과 같은 오브젝트여야 한다(`HackDriver`가 `GetComponent`로 찾음).
  계층이 달라 `RequireComponent`를 못 쓴다.

### 객체별 최소·최대 길이

`strokeLength` 하나를 `strokeMin`/`strokeMax`(월드 m)로 나눴다. `[FormerlySerializedAs]`로 기존 값 승계됨
(피스톤 7.5, 프레스 1 — 확인). 실측:

```
strokeMin=2, strokeMax=5 →  t=0: 2.000m   t=0.5: 3.500m   t=1: 5.000m
```

### 미리 늘여 놓고 시작

`startExtension`(0~1) 하나가 **에디터 씬 뷰 표시와 런타임 시작값을 동시에** 담당한다. `[ExecuteAlways]`라
슬라이더를 움직이면 그 자리에서 늘어나고, Play를 누르면 보이는 그 상태로 시작한다.

> **★ 홈 자세를 직렬화한 이유** — 에디터에서 늘여 놓으면 그 자세가 씬에 저장된다. 다음에 열 때 현재
> 트랜스폼을 홈으로 다시 재면 "늘어난 게 홈"이 되어 **열 때마다 더 늘어난다**(누적 파괴). `_parts`·
> `_headHomePos`를 `[SerializeField]`로 남겨 모든 계산이 그 값 기준이 되게 했다. 실측으로 정확히
> 원위치 복귀 확인(`t=0 → 0m / 0.8 → 6.0m / 0.3 → 2.25m / 0 → 0m`).
>
> 모델을 갈아끼웠을 때만 인스펙터 우클릭 → **"홈 자세 다시 캡처 (수축 상태에서만!)"**.

### 플릭 속도 분리

원인: **플릭과 홀드가 같은 시간(1초)을 써서 차이가 안 느껴졌다.**
`flickDuration` 신설 — **프레스 0.12초("쾅") / 피스톤 0.2초("철컥")**, 홀드는 1초 유지.
`Target` 대입 = 홀드 속도, `Flick()` = 플릭 속도. 플릭 도중 홀드가 들어오면 플릭이 취소된다.

### `[ExecuteAlways]`의 함정

에디터에서 `Update`는 **씬 뷰 리페인트 때만** 돈다 → 창이 뒤에 있으면 슬라이더를 움직여도 아무 일이
안 일어난다. `OnValidate` + `EditorApplication.delayCall`을 같이 걸어야 한다(OnValidate 안에서 트랜스폼을
직접 건드리면 경고가 난다).

## 3. 터렛 — 빙의에서 외부 조종으로

**빙의 대상은 이제 경비병·로봇팔 둘뿐이다.** CCTV·회전 장치는 보류(§8).

- `RotationPlatform`을 **회전판과 터렛이 같이 쓴다.** 차이는 `carryRiders` 하나뿐(터렛은 아무도 안 탄다).
  클래스를 나누면 값 튜닝을 두 번 하게 되므로 합쳐 뒀다.
- **각도 제한 기본 해제** (±360). 랩어라운드는 안 넣었다 — `GetNormalized`(VR 위치 제어 기준)가 정의되지
  않는다. ±360이면 퍼즐에선 사실상 무제한.
- 플릭 격자 30도(회전판 45도와 다르게 — 조준은 더 잘게).
- **발사는 자동.** 발사 버튼이 없다. 플레이어가 하는 일은 각도를 돌리는 것 하나뿐.

### 사격 판정 — 기준은 `everHacked`가 아니라 `captureState`

| 상태 | 쏘는 대상 |
|---|---|
| 조종 중 **아님** | **플레이어만** (경비병은 아군) |
| **조종 중** | **경비병만** (플레이어 안 쏨) |

**한 번 해킹했다고 영구히 안 쏘지 않는다 — 손을 떼면 다시 나를 쏜다.** 지나가는 동안 계속 붙잡고 있어야
한다. `everHacked`로 영구 무력화하면 "한 번 켜면 이기는 버튼"이 된다.
**빙의당한 경비병은 어느 모드에서도 안 쏜다**(콜라이더로는 구분이 안 되고, 실체는 내가 들어간 몸이다).

### 발사 연출

애셋(Smart Turret Template)의 애니메이터에 **`Shot` 트리거**가 이미 있었다. 그걸 쓴다.
**반동을 코드로 흔들면 안 된다** — `RotationPlatform`이 매 프레임 `localRotation`을 대입해 즉시 지워진다
(§1과 같은 소유권 문제). Animator는 그 아래 본을 움직이므로 안 싸운다.

**충돌 두 개 제거**: `STT_Turret` 비활성화(자체 타깃팅 + `rb.AddTorque` 조준이 우리 회전과 정면 충돌),
`Head`의 Rigidbody → `isKinematic`.

## 4. 경비병 감지 — 입체 부채꼴

`GuardDetection`이 `DetectRadius` 값만 든 껍데기였다. 실제 판정으로 다시 썼다.

- 좌우 각 25도(합 50도), 반경 `DetectRadius`
- **수직은 발밑~키 높이로 평행. 원뿔이 아니다** — 멀어져도 높이가 안 커지고, 머리 위로 지나가면 안 걸린다.
- 벽 투과 안 함. 키 높이는 `CapsuleCollider`에서 자동(경비병 1.94m).
- **빙의 중 플레이어 제외** — 안 그러면 "경비병이 경비병을 발각"이 되어 위장이 무의미해진다.

7개 케이스로 검증. 원뿔이 아님을 증명하는 줄:

```
정면 5.9m · 높이 1.8  →  걸림     (원뿔이면 이 높이는 범위 밖)
정면 3.0m · 높이 2.5  →  안 걸림  (키 1.9 초과)
대각 45°              →  안 걸림  (25° 초과)
```

**⚠️ 발각의 결과가 배선되지 않았다.** §6.4는 "발각 → 방 리셋"인데 리셋 시스템이 없다. 지금은
`OnDetected` 이벤트 + 로그만. 리셋이 생기면 그 이벤트 한 곳만 구독하면 된다.

## 5. 위험 표시 — 흑백 노이즈

`DangerNoise.shader` + `DangerZoneVisual.cs`. 경비병 부채꼴과 터렛 사선이 **같은 재질**을 쓴다 —
"이 격자 위에 서면 죽는다"가 한 가지 신호로 통일된다.

- **스크린 스페이스 UV.** 월드 UV면 먼 구역의 격자가 뭉개져 회색 면이 된다. 화면 기준이면 거리와 무관하게
  같은 밀도 — §7의 "3D에 붙지만 2D로 보인다"(해킹 테두리)와 같은 규칙.
- **Unlit.** 조명을 받으면 흑백 2치가 회색으로 무너진다.
- 터렛 사선은 **십자로 겹친 두 장**. 판 한 장이면 정면에서 선으로 수축해 격자가 안 보인다.
- 터렛의 반투명 빨강 원기둥은 삭제 — 경비병 표시와 생김새가 달라 "같은 종류의 위험"으로 안 읽혔다.
- **§7 색 언어를 아직 안 고쳤다.** "위험 범위 = 빨강"이 문서에 남아 있다 → 흑백 노이즈로 교체 필요.

> ⚠️ **미검증 위험**: 흑백 맵에 흑백 노이즈라 **배경에 묻힐 수 있다.** 실기로 보고 안 읽히면 테두리를
> 살리는 보정이 필요하다. 그리고 바닥 면만 그려 **높이 정보가 화면에 없다** — 공중에 뜬 부채꼴 아래는
> 실제로 안전한데 플레이어가 알 수 없다.

### 겪은 함정 — Unity의 "가짜 null"

`GetComponent<T>() ?? AddComponent<T>()`가 동작하지 않는다. 파괴됐거나 제대로 안 만들어진 유니티
오브젝트는 **null이 아닌 래퍼**로 돌아오고, `??`는 유니티가 오버로드한 `==`을 안 쓴다. `MissingComponentException`이
났다. `RequireComponent` 또는 `if (x == null)`로 검사해야 한다.

또 하나: `AddComponent<DangerZoneVisual>()` **실행 중에** `OnEnable`이 동기적으로 불린다. 그 안에서 다시
`AddComponent`를 하면 재진입이 되어 반쯤 만들어진 래퍼가 돌아온다.

## 6. 마일스톤(스테퍼) 양자화

경비병 제외 **모든 외부 조종 대상**에 적용(경비병은 빙의라 이 경로를 안 탄다).
`MilestoneStepper`(구조체) 하나를 `RailSet`·`RotationPlatform`·`ActuatorControl`이 공유.

6DoF 신호의 떨림·아웃라이어를 **자르지 않고 양자화**한다. 누적 후 스텝 단위로만 출력.

> **★ 스텝 ÷ 간격 = 최대 속도.** 따로 정할 수 없다. 간격을 딸깍 빈도로 고정(0.0833초 = 초당 12틱)하고
> 스텝을 부품 속도에서 유도한다 → 튜닝 손잡이가 "속도" 하나로 유지된다.
> 터렛 60°/s → **5도**(감으로 말한 값과 정확히 일치), 레일 2 m/s → 0.17m, 액추에이터 0.6/s → 0.05.

```
30·45·60·72fps → 12틱 / 60.0°s      90fps → 11틱 / 55.0°s (프레임 경계, 무해)
떨림 ±1도 진동 1초 → 0.0도          200도 스파이크 → 즉시 5도, 잔량 5도(상한 2스텝)
```

**잡은 버그**: 처음엔 "쿨다운>0이면 깎고 return" 구조라 0이 되는 프레임을 한 번 더 버려 **60°/s 요구에
실측 50°/s**가 나왔다. 먼저 깎고 판정 + 쿨다운을 `=` 대신 `+=`로 누적(남은 음수 시간을 다음 주기로 넘김).

**잔량 상한(2스텝)이 필요한 이유**: 없으면 최대 속도를 넘게 요구한 만큼 쌓여 **손을 뗀 뒤에도 밀린 딸깍이
줄줄이 나온다.**

**`ActuatorControl`에 `Update`를 따로 둔 이유**: `HackDriver`는 **입력이 있을 때만** `Drive`를 부른다.
그러면 쿨다운이 안 흐르고 잔량이 남아 다시 잡는 순간 튄다. 레일·회전판은 자기 `LateUpdate`에서 매 프레임
돌리므로 이 문제가 없다.

**플릭에는 안 걸린다.** 각본된 이동이고 자체 곡선이 있어 이중 양자화가 되면 덜덜거린다.

## 7. ⏸ 레일 세트 — 의도적 보류

**컴포넌트는 동작하지만 수치가 전부 미확정이다.** 맵이 아직 세로 레일뿐이고, 곧 불러올 스테이지에
**레일 캐리어를 여러 개 이어붙인 것**이 있어 그것을 보고 하드코딩하기로 했다. 상세는
[기초_설계안 §6.2 "⏸ 레일 세트"](design/기초_설계안.md)에 전부 기록했다. 요점:

- 모델 8.92m vs 칸 간격 2m = **4.5배 불일치.** 그대로 갈아끼우면 다섯 칸이 겹친다.
- `Model_Rail`은 **한 줄**(파츠 z가 한쪽에 몰림). 두 줄은 Z로 두 개 놓는 것.
- 플릭이 **걷기의 5배로 너무 빠르다**(0.28초 × 2m ≈ 7.1 m/s). 칸 길이 정할 때 같이 잡는다.
- **필요 총 길이 = 보이는 구간 L + 2 × max(rangeMax, |rangeMin|).** 칸 수는 손으로 정하는 값이 아니라
  범위에서 계산되는 결과다.
- **⚠️ `RailSetEditor` 경고식이 틀렸다** — `railTotal < span`만 봐서 통과해도 레일 끝이 드러난다.
- **⚠️ 드로우콜**: 레일 1개 = 렌더러 96개·정점 12,430. 30칸이면 5,760 렌더러 → 모바일 VR에서 죽는다.
  머티리얼이 1종이라 `Mesh.CombineMeshes`로 렌더러 1개로 결합하면 해결(정점 22만 → `IndexFormat.UInt32`).
- `RailSet.prefab`이 없다 — 씬 직접 배치라 재사용·팔레트 등록 불가.
- `railLength` → **`cellLength`로 rename**(`FormerlySerializedAs`로 값 승계). 모델 길이와 무관한 값임을
  이름으로 분명히 했다.

## 8. CCTV · 회전 장치 보류

시간·단순화로 이번 범위에서 제외. **삭제가 아니다.**

- 프리팹을 `Prefabs/Hackables/Deferred/`로 이동. `PrefabPaletteWindow`가 이 그룹을 **맨 아래·기본 접힘 +
  경고 문구**로 표시한다. 배치 자체는 막지 않았다.
- `HackableKind`의 **열거형 순서는 안 바꿨다.** 저장된 int라 자리를 옮기면 기존 프리팹의 종류가 뒤바뀐다.
  주석으로만 표시하고 `DefaultControlType()`에서 터렛만 옮겼다. **이 경고를 파일 상단에 박아 뒀다.**
- 회전 장치 코드(`RotationPlatform`)는 **터렛이 쓰므로 계속 검증된다.**
